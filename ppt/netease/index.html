02

两个业务 skill

UU 取号 · G66 部署

Business Skills
06
UU 取号：从一台台手装到并行批量
痛点
给远程 PC 配 UU 远程，以前要一台一台手动装客户端，再逐个取设备 ID 与验证码；取到的号记在 txt 或表格里，零散、没规范。
我的解决方案
引入 agent + skill 的方式实现，能够灵活处理各种分支情况：运行环境的检查，安装状态的检查，软件界面是否在桌面可见，是否开启他人远程协作按钮等。
成果
并行高效，低成本
从一台台手装到一次发起多台，10 台设备以前人工装需要 2 个多小时，现在只需要 10 分钟，每一台成本在 1 元以内。
07
G66 部署：从人工逐台到自动完成
痛点
人工一台一台去准备游戏环境（100GB 的量级），从 0 到 1 的下载到准备完成往往需要花费 3~4 个小时，启动脚本能否正常启动还得人工确认。
我的解决方案
引入 agent + skill 的方式实现，自动判断目标机状态，自动传输，启动后自动验证。
阶段 1 · 正常流程
从官网下载安装包，下载 patch，替换引擎
阶段 2 · 内网分发
传输快，极大地提升效率
成果
提效明显
3 小时压缩到 30 分钟左右。

评测系统

判题思想 · 跑测闭环 · 过程可视化 · 选型结论

Evaluation System
09
评测系统：动机与三指标
skill 能把需求自动化完成，但它的瓶颈在哪儿？内部实现细节又是怎样的？
在提示词等前置环境不变的情况下，哪种 agent 搭配哪种模型，才能最高效、低成本、稳定地完成自动化需求？
从三点核心指标出发，量化任务的跑测结果
① 成功率
SR
任务是否真正达成目标
② 耗时
Duration
任务跑完用了多久
③ 成本
Cost
单次任务花了多少钱
10
评测系统的判题思想与跑测闭环
判题思想 · 判世界
① 看影响：只看 agent 操作之后世界实际发生了什么变化，不读模型的自述
② 读真值：从这些影响里读出客观的事实真值
③ 比预期：与预期答案对比，判定成败
判的是「世界发生了什么」，不是「模型说了什么」。
跑测闭环 · 自主设计一张 L1–L4 能力卷（能力阶梯，业务解耦可复用）
L1 单步操作
能跑通基本指令
L2 复合操作
装包、传文件、起进程
L3 真实场景
多步串联，如配 UU 再写 DK
L4 诚实判决
面对失败与干扰如实汇报
发起跑测：多 agent × 多模型 × 多设备，批量并发，同一套题目横向对齐；结论由目的驱动。
同一张卷子、同一批设备、同一组题目——结果才可比。
